In total, **56 configurations and 168 chronological development-fold evaluations** were run, followed by six held-out evaluations, two direct runtime-gate replications, and two full native training diagnostics. This is a bounded empirical search, not an exhaustive proof over every possible feature subset or estimator.

The 19-feature candidate was selected using the predeclared mean-fold-AUC rule. It is not uniformly better: the 20-feature baseline has slightly higher pooled development AUC and lower held-out ECE at seed 42. **None of the 56 configurations met the chronological development ECE limit of 0.10**; the lowest observed ECE was 0.1138. The best supplementary mean-fold result was the 27-feature logistic model with added liquidity inputs: mean AUC 0.5865 and ECE 0.1198.

The 19-feature held-out AUC improvement at seed 42 was approximately 0.0055. Its paired 95% interval, resampling both scan groups and symbols, was **[-0.0231, 0.0355]**. The candidate's absolute AUC interval includes 0.50. All three seeds' paired intervals include zero. The much narrower scan-only intervals in `holdout.json` condition on the observed securities within each scan; use `two_way_uncertainty.json` for the fuller uncertainty assessment. Even these estimates have only three temporal groups and do not establish robustness across market regimes.

The existing numerical gate passes at both 19 and 20 features, but its implementation uses shuffled symbol-group folds and falls back to unpurged fitting when temporal purging collapses. Both direct gate replications logged **5/5 unpurged folds**. This differs from the declared `chronological_contiguous_group_purged_weighted_kfold_v2` contract string. Treat the native numerical passes as diagnostics rather than forward-performance validation. The temporal-purge limitation is already discussed in repository ERR-066. No gate or contract was weakened or changed during this review.

Additional limits: 1,173 complete rows have a stored `t1` shorter than the seven-hour target horizon. The chronological study conservatively used the later of the recorded endpoint and event start plus seven hours, avoiding under-purging. Native training diagnostics deliberately used the repository's existing training behavior and stored intervals. Most rows' active-HMM replay timestamps postdate their historical scan dates; the successful lineage check establishes consistency, not an end-to-end point-in-time HMM validation. The study did not refit the upstream HMM separately within each fold. The pool is backtest evidence, and its existing engine assumptions remain applicable.

For a new production candidate, **20 features remain the current supported profile**. Nineteen is a defensible research candidate because it removes the only incomplete feature in this pool, but promotion would require a supported profile change and adequate independent validation. Increasing to 42 recorded features did not resolve the measured development failure. The available evidence does not establish an exact sufficient feature count or an exact number of additional rows needed. The next useful evidence is new mature scan groups with complete decision-time features and observed path-based labels; the existing held-out cohort is now consumed and must not be repeatedly used for selection.
